# Derived CPU telemetry specifications

Arm has not published telemetry specifications for the cores in this directory. Each file is
generated by `tools/topdown_tool/scripts/derive_cpu_spec.py` from the closest core that has an
official specification, filtered against the target core's PMU event list from
[ARM-software/data](https://github.com/ARM-software/data/tree/master/pmu), and adjusted where
measurements on hardware showed that a base formula does not hold.

The files carry `"quality": "Development"`. Treat their metrics as a best effort, not as an
official Arm release. When Arm publishes an official specification for one of these cores,
point `mapping.json` at it and delete the derived file.

| Core        | MIDR part | Base specification | Slots | Metrics kept | Changes from the base |
|-------------|-----------|--------------------|-------|--------------|-----------------------|
| Cortex-X4   | 0xd82     | Cortex-X925        | 10    | 67/67        | None. Every event used by X925 metrics exists on X4 with the same code. |
| Cortex-A720 | 0xd81     | Cortex-A725        | 5     | 63/67        | `frontend_core_flow_bound` dropped (no `STALL_FRONTEND_FLOW`). Backend cache split rewritten, frontend cache split dropped (see below). |
| Cortex-A520 | 0xd80     | C1-Nano            | 3     | 66/119       | CME/SME/SVE/LSE metrics dropped (events not implemented). `backend_core_bound` dropped (no `STALL_BACKEND_CPUBOUND`). Cache split metrics dropped (see below). |

When a metric is dropped, its children in the topdown decision tree are attached to its parent,
so the rest of the subtree stays reachable. For example, on A520 `backend_stall_interlock_bound`
and `backend_busy_bound` sit directly under `backend_bound`.

## How the base was chosen

Each base is the direct successor of the target core with the same pipeline width and PMU event
encoding: X4 → X925, A720 → A725, A520 → C1-Nano. The script rejects any event whose code differs
between the base specification and the target core's event list, so every kept metric uses the
same hardware events as on the base core.

## Hardware measurements (Snapdragon 8 Gen 3 / SM8650, simpleperf)

Measured with small static microbenchmarks pinned to one core type: a high-IPC integer loop, a
random pointer chase with working sets from 16 KB to 128 MB, a 64-bit divide chain, and random
calls into code footprints from 16 KB to 32 MB.

**Slots.** `(STALL_SLOT + OP_SPEC) / CPU_CYCLES` in the high-IPC loop was 3.07 (A520), 4.97
(A720) and 9.6 (X4), matching the bases' `num_slots` of 3, 5 and 10. The kernel's `caps/slots`
reports 10 for all cores on this SoC, so it cannot be used on heterogeneous systems.

**Topdown level 1.** `STALL_SLOT + OP_SPEC` stays within 1% of `slots × CPU_CYCLES` on all three
core types for memory-bound, frontend-bound, divide-bound and high-IPC workloads, so
`frontend_bound + backend_bound + retiring + bad_speculation` adds up to about 100%.

**Cortex-A720 backend cache split.** The base formulas assume `STALL_BACKEND_L1D` and
`STALL_BACKEND_MEM` are disjoint. On A720 they overlap: with an L2-resident working set
`L1D/MEMBOUND ≈ 0.99` and `MEM/MEMBOUND ≈ 0.96`, so the base `backend_mem_cache_bound` reached
171%. A720 counts L1D stalls for any L1 data miss, including those that also miss L2. The derived
spec uses:

- `backend_mem_cache_bound = STALL_BACKEND_L1D / STALL_BACKEND_MEMBOUND * 100`
- `backend_cache_l1d_bound = (STALL_BACKEND_L1D - STALL_BACKEND_MEM) / STALL_BACKEND_L1D * 100`
- `backend_cache_l2d_bound = STALL_BACKEND_MEM / STALL_BACKEND_L1D * 100`

With a DRAM-sized working set, `STALL_BACKEND_MEM` can exceed `STALL_BACKEND_L1D` by a few
percent, so `backend_cache_l1d_bound` may read slightly below 0% (-2.3% measured) and
`backend_cache_l2d_bound` slightly above 100%. Read these as 0% and 100%.

**Cortex-A720 frontend cache split.** `STALL_FRONTEND_L1I` and `STALL_FRONTEND_MEM` behave
neither as disjoint nor as nested counters (for a 32 MB code footprint `L1I/MEMBOUND = 0.83`,
`MEM/MEMBOUND = 0.92`; for 32 KB, 0.93 and 0.61). `frontend_mem_cache_bound`,
`frontend_cache_l1i_bound` and `frontend_cache_l2i_bound` are dropped. `frontend_mem_bound`,
`frontend_mem_tlb_bound` and the L1I/L2/LL cache effectiveness groups remain.

**Cortex-A520 cache split.** On this SoC the A520 pair shares an L2 ("per-complex L2"). As the
A520 TRM describes for that configuration, `STALL_BACKEND_L1D` excludes cycles counted by
`STALL_BACKEND_MEM`, but in practice it stays near 0 (≤ 4% of `STALL_BACKEND_MEMBOUND` at every
working-set size, including L2-resident ones), and `STALL_FRONTEND_MEM` stays near 0 even with an
8 MB code footprint. The L1D/L2D and L1I/L2I split metrics would therefore always read about
0%/100%, so they are dropped. `backend_mem_cache_bound` and `frontend_mem_cache_bound` (the sums)
are kept and behave as expected.

**Cortex-X4.** The base formulas held: `STALL_BACKEND_L1D` and `STALL_BACKEND_MEM` are disjoint
(`L1D + MEM ≈ MEMBOUND` at all working-set sizes), and so are `STALL_FRONTEND_L1I` and
`STALL_FRONTEND_MEM`.

## Cortex-A520 event aliases and fallback

C1-Nano names two implementation-defined events differently from A520. The script maps them with
`--alias` because the A520 descriptions match:

- `IMP_STALL_BACKEND_ILOCK_VPU` → `STALL_BACKEND_ILOCK_VPU` (0xe6 on both cores): interlock on a
  vector/FP source.
- `IMP_STALL_BACKEND_BUSY_VPU_ARB` (0xef) → `STALL_BACKEND_BUSY_VPU_HAZARD` (0xed): stall because
  the VPU shared with the paired core is busy.

`l1d_cache_miss_ratio` uses the Cortex-A725 formula `L1D_CACHE_REFILL / L1D_CACHE`, because the
C1-Nano formula needs `L1D_CACHE_RW`.

## Regenerating

From `tools/topdown_tool`, with `S=../../data/pmu/cpu/specifications`:

```sh
uv run python scripts/derive_cpu_spec.py --base $S/cortex/cortex_x925_r0p0_pmu.json \
    --events cortex-x4 --product-name Cortex-X4 --part-num 0xd82 \
    -o $S/derived/cortex_x4_derived_pmu.json

uv run python scripts/derive_cpu_spec.py --base $S/cortex/cortex_a725_r0p0_pmu.json \
    --events cortex-a720 --product-name Cortex-A720 --part-num 0xd81 \
    --override-metric 'backend_mem_cache_bound=STALL_BACKEND_L1D / STALL_BACKEND_MEMBOUND * 100' \
    --override-metric 'backend_cache_l1d_bound=(STALL_BACKEND_L1D - STALL_BACKEND_MEM) / STALL_BACKEND_L1D * 100' \
    --override-metric 'backend_cache_l2d_bound=STALL_BACKEND_MEM / STALL_BACKEND_L1D * 100' \
    --drop-metric frontend_mem_cache_bound --drop-metric frontend_cache_l1i_bound \
    --drop-metric frontend_cache_l2i_bound \
    -o $S/derived/cortex_a720_derived_pmu.json

uv run python scripts/derive_cpu_spec.py --base $S/lumex/arm_c1_nano_r0p0_pmu.json \
    --events cortex-a520 --product-name Cortex-A520 --part-num 0xd80 \
    --alias IMP_STALL_BACKEND_ILOCK_VPU=STALL_BACKEND_ILOCK_VPU \
    --alias IMP_STALL_BACKEND_BUSY_VPU_ARB=STALL_BACKEND_BUSY_VPU_HAZARD \
    --fallback $S/cortex/cortex_a725_r0p0_pmu.json \
    --drop-metric backend_cache_l1d_bound --drop-metric backend_cache_l2d_bound \
    --drop-metric frontend_cache_l1i_bound --drop-metric frontend_cache_l2i_bound \
    -o $S/derived/cortex_a520_derived_pmu.json
```

`--events cortex-x4` downloads `pmu/cortex-x4.json` from ARM-software/data; a local path or URL
also works. The script validates its output with the topdown-tool specification loader.

## Other cores

For a core that is not listed here, derive a specification the same way and either pass it with
`topdown-tool --cpu <file>.json` or add it to `mapping.json`. Before trusting the results:

1. Check that the core implements `STALL_SLOT`, `STALL_SLOT_FRONTEND`, `STALL_SLOT_BACKEND`,
   `OP_SPEC`, `OP_RETIRED` and `STALL_FRONTEND_FLUSH` (topdown level 1).
2. Measure the slot count as described above. If it differs from the base, pass
   `--num-slots N --rewrite-slots`.
3. Check whether the cache stall events are disjoint or nested on that core
   (`L1D + MEM ≈ MEMBOUND` means disjoint) and use `--override-metric` / `--drop-metric`
   accordingly.
